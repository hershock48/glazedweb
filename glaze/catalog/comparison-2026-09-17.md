For each concern the [R01 inventory](inventory-2026-09-17.md) tabulated: one row per implementation, the strongest one with the evidence, the reuse boundary (the exact functions that would become the shared package and what stays behind), and which of the inventory's twenty questions the concern answers. **Questions answered.** 4 and 19.

- Q4 idempotency: two contracts, not one with two adapters. Order acceptance settles once into one of three terminal outcomes (accepted, rejected, cancelled) inside a single statement. A payment attempt has five states (prepared, processing, unknown, completed, failed) with a provider call between claim and settle, retry generations (`retryOf`) and an owner review path. They share only the identity shape: a client UUID v4 plus a sha256 fingerprint, replay on match, 409 on mismatch. Of the two fingerprints, copperac's `requestFingerprint` (key-sorted, depth 16) is the one to keep; DeVine's `paymentFingerprint` is `JSON.stringify` of a chosen subset and is key-order dependent, which is the same class of problem the re-review found in DeVine's gateway identity comparison (jsonb reordered keys). DeVine's unpaid path is out of scope for order-acceptance today: it deliberately allows a memory backend ("the email is the order", route lines 32 to 37), and order-acceptance refuses memory in production. Adopting it there means requiring Postgres for unpaid florist orders, which is a Kevin decision, not an extraction step.
- Q19 carts: out of scope. Each storage choice is argued in its file header (Louie's cookie so the header count and the add button work with scripting off; DeVine `sessionStorage`; Sprinkles `localStorage`; copperac keeps only the attempt reference in `sessionStorage`). The contract covers what the server receives: item id, quantity, group-qualified picks, the reviewed totals.

**Where the provider-independent line sits.** `payment-engine.ts`, 41 lines, imports nothing: `runPayment(repo, key, fingerprint, snapshot, charge, retryOf)` with the `AttemptRepository` interface (`prepare`, `claim`, `settle`, `read`), the five `AttemptState` values, the four `AttemptOutcome` kinds and the `PaymentNotSubmitted` boundary ("only throw this before CreatePayment"). One thing inside it is not provider-independent: line 37 maps `result.status` against the strings `COMPLETED`, `FAILED`, `CANCELED`, which are Square's vocabulary. The extraction moves that mapping into the adapter, so `charge` returns an engine state, not a provider status. The Postgres repository (`payment-attempts.ts`) is the second shareable piece, parameterized by table name. Adapters stay separate: Square is `payments.ts` plus `client.ts` plus `oauth.ts` (server-side CreateOrder and CreatePayment); Stripe is Anchor's `stripe.ts` plus a Checkout Session step (hosted redirect, settled by webhook or return page, never a synchronous charge); Toast is a link and a host gate. Nothing forces the three into one flow: the engine models "we asked a provider to take money and may not have heard back", which is the Square shape; Stripe hosted Checkout enters the engine at `unknown` and is settled by `settleProviderPayment` from the webhook, which is exactly how DeVine's webhook path already works.
